The rule
Do not build anything from scratch until you have audited what already exists. Kanida has several engines, backends, an AWS account and a database from earlier versions. Your first job is to inventory them, cross-check them against the requirements list below, and propose the smallest architecture that stitches them into one product. Only after the founder approves that proposal do you build the gaps.
What Kanida is (one paragraph)
A mobile-first, AI-based research app for Indian retail traders and investors. Three transparent managers — Trader (1–3 day, Falcon rulebook), Investor (3–12 month, 10–15 names, monthly rebalance), Pathfinder (research lab that forward-tests hypotheses and publishes what died) — each with a rulebook, a risk budget, virtual money, and a public, losers-first, cost-adjusted track record. Plus a daily market base-rate feed, a creator console that turns publishable facts into content with referral links, and a one-tap broker hand-off where the user confirms every order inside their own broker. Kanida never places an order. One codebase ships Android, iOS, web and tablet.
Non-negotiables (enforce in code)
No return promises or target prices anywhere (content lint).
Every return rendered with its drawdown; expectancy is the hero metric, never win rate.
Losers shown first on every trade list.
Every number carries n, date range, data source and cost convention; n<50 flagged, n<20 greyed.
Point-in-time only: any price read takes an as_of date; no look-ahead, no survivorship.
Backtests appear only on methodology pages, labelled “Simulated · Not traded · Not PaRRVA-verified”.
Signals, marks, approvals, corrections are append-only; nothing edited in place.
Nothing reaches a customer without an RA approval row. Signals never reach the creator console.

Step 1 — Audit (deliver docs/audit.md before any code)
Inventory every existing repo, service, engine, script, database, and AWS resource. For each: what it does, language/stack, data it reads and writes, whether it runs today, test coverage, and what it would take to reuse. Include: Falcon V7 and any other signal engines, the arena / challenger pipeline, the pattern-mining and NDP work, the Zerodha auto-trade code, any backend/API, any existing app or landing page, the DB schema, and the AWS setup (region, compute, DB, storage, secrets, monitoring). Note anything not in an India region.
Step 2 — Requirements checklist (cross-check each against the audit)
Mark each HAVE / PARTIAL / MISSING, name the existing component if any, and say what is needed to make it product-grade.
Data - R1 Historical daily + 1-min bars, adjusted, with point-in-time universe (Nifty 500 / F&O). Source: Kite Connect (founder’s account) — the only source for now. One thin MarketData interface in front of it so a licensed source can be swapped in later without touching product code. Do not build other adapters unless the founder says so. - R2 Daily data-quality check (17:30 IST): completeness, gaps, corporate actions; on failure, no signals and a public “no signal today” state.
Engine - R3 Signal generator per manager from a deterministic rulebook, 18:00 IST nightly, append-only with hash chain, reproducible. - R4 Book engine: marking convention (09:15 first-bar open entry, rule exits, 15:29 EOD), costs (brokerage, STT, exchange, 10 bps slippage, versioned), expectancy, win/avg-win/avg-loss, max and current drawdown; closed-trade ledger; 2× slippage sensitivity run. - R5 Pathfinder runner: each hypothesis = its own virtual book; status queued→running→passed/died→promoted; post-mortem required on death; weekly digest data. - R6 Base-rate engine: founder’s 10–15 observation rules run daily with count, base rate, n, regime; regime detector (breadth, VIX bucket, expiry proximity).
Review & compliance - R7 RA review queue: approve/reject each signal with a note; publish only approved at 20:00; audit log. - R8 Auto disclosure line on every idea (RA name/number, holdings/conflict statement, market-risk disclaimer). - R9 Compliance classifier for creator content: PUBLISHABLE vs KANIDA-ONLY. Hard blocks: ticker + directional verb; any price/target/stop; any Kanida performance figure; banned phrases; any manager position. Founder review queue at 100% for the first 8 weeks. - R10 PaRRVA submission of approved recommendations (API when founder provides access; file-upload fallback). Badge shown only when verified. - R11 Public corrections log.
Customer app (one Expo codebase → Android, iOS, web, tablet; screens per approved prototype) - R12 Home (three manager cards: expectancy + drawdown + n + live-since + today). - R13 Idea card (rule, invalidation, base rate with n, thesis, sizing to user capital, disclosure, “Send basket”). - R14 Track record (metrics, outcome distribution, losers-first ledger, “how we count”, PaRRVA badge, methodology link). - R15 What I got wrong + corrections log. - R16 Market base-rate cards. R17 Pathfinder digest + graveyard. R18 Regime / Today panel (+ optional “your mirror” from linked broker). - R19 Methodology page per manager (rulebook, convention, labelled backtests, sensitivity). - R20 Account: OTP login, e-KYC before first payment, plan, GST invoices, alerts, investor charter / complaints route. - R21 Free tier = books delayed one day; Pro ₹299/mo or ₹2,999/yr founding (list ₹4,999); Intelligence ₹599/mo or ₹5,999/yr; AutoTrade tier in schema only, disabled.
Execution - R22 Zerodha Kite Publisher basket hand-off (user confirms in Kite). Log the hand-off, never an order. Dhan/Upstox baskets later. - R23 Optional “Login with Zerodha” (Kite Connect) if Rainmatter grants access: read holdings/funds for sizing and mirror; per-user session only; never store or pool a user’s tick data.
Creator engine - R24 Console: Discover (classified feed by audience type) · Create (script, thread, carousel outline, chart, talking points) · Customize (tone, English/Hindi, creator name) · Publish (attribution + content ID + referral link/code embedded) · Earn (funnel, MRR, commission, month-1/3/6 retention, earnings per content piece). - R25 Referral: kanida.ai/<handle> + promo code; one subscriber → one creator; 30-day last click; code overrides link; refund clawback; self-referral / same-device / same-instrument blocks; monthly payout export with 2% TDS against PAN. - R26 Commission config: 25% of first-12-month payments, then 10% while active. Creators have no access to ideas, positions or performance (enforce at API).
Platform - R27 Payments: Razorpay — annual single payment; monthly via UPI Autopay / card e-mandate; pro-rata refund; GST-inclusive display and invoices. - R28 Analytics events for the launch gates: view all three managers, send basket, start trial, pay, cancel, referral click/signup, creator publish; admin gate dashboard. - R29 Runbook automation: 17:30 · 18:00 · 18:15 · 20:00 · 08:45 · 09:10 · 09:15 · 15:35 jobs with health checks and founder alerts; failure drill script. - R30 Security: India-region hosting, encryption, role-based access (customer / creator / RA / admin), admin audit, backups + restore test, secrets manager, docs/security_policy.md.
Step 3 — Architecture proposal (deliver docs/architecture.md; wait for approval)
Propose the smallest structure that reuses what exists: which existing engines become R3–R6 as-is or with wrappers; what the single backend/API is; how the Expo app talks to it; what runs where on the current AWS; what is retired. One diagram, one page. List the gaps in build order. Do not start building until the founder replies “approved”.
Step 4 — Build the gaps, in this order
Signal generator running nightly on the Trader rulebook (the record clock starts here). 2. Book engine + metrics tests + data-quality gate. 3. Investor book, Pathfinder runner, base-rate engine. 4. RA review + disclosure + audit log + classifier v1. 5. Expo app screens on real data; methodology; PaRRVA client; analytics. 6. Kite Publisher hand-off; referral system. 7. Creator console. 8. Auth, KYC, Razorpay, entitlements, Earn dashboard; EAS builds. 9. Alerts, corrections log, sensitivity, security, runbook automation. 10. Hardening, load test, payout export, gate dashboard.
Out of scope until Phase 2: automatic order placement / OMS, real-time display data, Creator Pro, user-submitted hypotheses, direct posting, US market.
Founder inputs (stub the interface, list what is missing in every hand-back)
Trader rulebook (deterministic) · Investor rulebook · first 5 Pathfinder hypotheses · 10–15 observation rules · cost values · Kite credentials · RA name/number + holdings list + disclaimers · PaRRVA access · e-KYC vendor, Razorpay, GSTIN · legal copy · 50 labelled classifier examples · Kite Connect startup access (if granted).
Hand-back format
docs/handbacks/<n>-<module>.md, under one page: what was built · how to run · test results · evidence (reconciliation, screenshots) · missing founder inputs and what is stubbed · risks · next step. Update CLAUDE.md if a decision changed.
